# ChronoSync 可行性分析

| 项目 | 内容 |
| --- | --- |
| 分析对象 | ChronoSync 1.0.2 |
| 分析日期 | 2026-11-06 |
| 结论 | **有条件可行：可信内网 + root SSH + 人工触发 + 明确安全边界** |
| 决策建议 | 维持 1.0.2 发布；新功能/安全增强进入后续版本 |

## 1. 分析范围

分析覆盖技术、运营、经济、进度、安全、合规和可维护性。功能实现细节见 [实施方案](实施方案.md)，证据见 [实测证据与复现](实测证据与复现.md)，风险明细见 [审计报告](审计报告.md)。

## 2. 技术可行性

### 2.1 已具备的技术条件

| 能力 | 实现 | 证据 |
| --- | --- | --- |
| 标准时间 | 多源 SNTP，1.5s 超时，中位数/0.5s 离群过滤，选最低 RTT | `src/ntp.rs`；4 个单元测试 |
| 远程执行 | russh，密码认证 + keyboard-interactive 回退 | 真实设备只读测试（11/12 可达） |
| 时间写入 | `date -u -s @epoch`，UTC 字符串回退 | mock SSH + 真机计划；未在生产设备写入 |
| RTC | `hwclock -w`；x86 无 RTC 节点时 direct ISA 探测/写入；无 RTC 跳过 | 单元测试 + 代码审查 |
| 多发行版 | 只依赖 `date`，可选 `hwclock`/`timedatectl`/tzdata | Debian/Arch/Gentoo/Buildroot/BusyBox 只读验证 |
| 单文件 WebUI | `include_str!` 嵌入 | 六平台二进制健康接口 |
| 部署 | systemd/OpenRC/procd/AudioSys/BusyBox 自动识别 | install dry-run 与平台审查 |
| 跨平台 | Linux x86 v1–v4、ARM64、Windows x86_64 | 构建矩阵 + 启动验证 |

### 2.2 技术难点与结论

1. **异构固件命令差异**：用 POSIX sh、命令探测和可选步骤降级解决；不假设 `hwclock`/`timedatectl` 存在。
2. **NTP 可信性**：普通 SNTP 无法认证，采用多源共识和失败锁定降低单源错误风险；不能消除恶意时间源。
3. **SSH 主机密钥**：为兼容大量设备当前接受任意主机密钥；这是明确的安全折衷，不适合不可信网络。
4. **跨平台构建**：MinGW 和 AArch64 交叉工具链已跑通；glibc 版本要求 2.39，旧系统需源码构建。
5. **静态编译**：当前发布物为动态 glibc，静态 musl 方案可行但未纳入 1.0.2；限制和步骤见编译文档。

结论：在可信内网、可控 SSH 凭据、人工触发的前提下，技术路径成立。

## 3. 运营可行性

### 3.1 使用流程

现场人员只需浏览器：填设备 → 仅检测 → 一键校时 → 看日志/下载。无需在每台目标安装软件，不需要目标访问外网，适合音频设备、嵌入式设备和临时维护。

### 3.2 运维负担

- 控制机需要能访问目标 SSH 和 NTP。
- 目标机需允许 root 登录；这与“最小权限”原则冲突，但符合当前设备固件现实。
- 控制台默认监听局域网，必须通过 `--auth`、网络隔离或 SSH 隧道收紧。
- 目标机已有的 NTP/chrony 服务可能再次改写时间；工具只做一次性校准，不接管目标时间服务。

结论：运营流程简单，但必须把“可信内网 + 维护窗口 + 先检测后写入”写成硬规则。

## 4. 经济可行性

- 软件为 MIT 开源，无按设备授权费。
- 控制机可用现有 Linux/Windows 机器；目标无需额外硬件。
- 主要成本是开发维护、测试设备和安全评审。
- 与逐台登录相比，批量操作减少人工时间，但单次校时的直接经济收益取决于机群规模。
- 静态构建、代码签名、集中审计属于后续增强，不是当前必需成本。

结论：在当前规模下成本合理；不建议为小规模机群引入服务器端数据库或常驻代理。

## 5. 进度可行性

1.0.2 已完成 Wave 1–4、六平台构建、真机只读测试、打包和 GitHub 发布。剩余工作是文档基线和后续优化，不再阻塞 1.0.2。详细排期见 [项目管理与排期](../项目管理与排期.md)。

24 小时长稳测试已按项目决定取消，不作为进度或验收阻塞项；该决定记录在文档基线和验收记录中。

## 6. 安全与合规可行性

| 风险 | 等级 | 当前控制 | 残余风险 |
| --- | --- | --- | --- |
| 控制台无 TLS | 中 | 可信内网、`--auth`、可绑 127.0.0.1 | 局域网嗅探 |
| SSH 密码在浏览器/内存 | 中 | 默认不持久化；日志脱敏 | 浏览器扩展/主机被攻陷 |
| 记住密码 localStorage | 中 | 默认关闭、显式提示、清除设备 | 本机其他用户/恶意脚本 |
| 主机密钥不固定 | 中 | 文档警示、可信网络 | 中间人 |
| NTP 未认证 | 中 | 多源、失败锁定 | 恶意/错误时间源 |
| root SSH | 高 | 受控网络、最小设备集 | 凭据泄露导致主机接管 |

结论：可作为**内部运维工具**使用，不可作为公网服务或高合规环境的唯一校时手段。若需更高保证，应增加 TLS 反向代理、主机密钥固定、专用低权限账号和审计日志。

## 7. 备选方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 本工具（控制机 SSH） | 无目标代理、兼容异构固件、单文件 | 依赖 root SSH、无 TLS | **选用** |
| 目标机安装 chrony/NTP | 标准化、长期稳定 | 需改固件、目标需外网/内网源 | 不替代，可共存 |
| Ansible/Salt 批量执行 | 成熟、可编排 | 依赖 Python/代理、嵌入式支持差 | 过重 |
| 厂商管理平台 | 集成度高 | 绑定厂商、成本高 | 不通用 |
| 手工逐台校时 | 零开发 | 慢、易漏、不可审计 | 仅应急 |

## 8. 可行性结论

**有条件 GO**：

1. 只在可信管理网部署，默认启用访问认证或绑定回环。
2. 目标机 root SSH 凭据按最小范围管理，不进入仓库/日志/工单。
3. 上线前必须“仅检测”，确认网络、时区、偏差和 RTC 状态。
4. 1.0.2 已满足当前运维需求；主机密钥固定、TLS、静态构建、代码去重作为后续版本候选。
5. 不将 24 小时长稳测试作为本版条件；未来若恢复，必须按独立测试计划执行，不能补写结果。

详细风险与审计结论见 [审计报告](审计报告.md)；开放项见 [Issues 整理](Issues整理.md)。
