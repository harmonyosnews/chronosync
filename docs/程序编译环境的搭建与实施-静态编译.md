# 程序编译环境的搭建与实施：动态发布与静态编译

| 项目 | 内容 |
| --- | --- |
| 适用版本 | 1.0.2 |
| 当前发布形态 | Linux 动态链接 glibc（要求 ≥ 2.39）；Windows MinGW；ARM64 GNU |
| 静态发布状态 | **未产出、未声明支持**；本文件给出可执行方案与验收门槛 |
| 关联 | [构建报告](../reports/BUILD-1.0.2.md)、[闸门](纪律与闸门.md) |

## 1. 目标与边界

本文解决两件事：

1. 复现 1.0.2 的正式构建环境（动态 glibc + Windows + ARM64）。
2. 说明如何新增静态 musl 构建，以及为什么当前发布包不是静态的。

静态构建不是“加一个 flag 就完成”：ring 的 C/汇编、DNS/NSS、时区数据、交叉链接器和运行时行为都要重新验证。没有完成验证前，不能把 musl 产物写进 Release 或声称“无依赖”。

## 2. 正式构建环境（1.0.2 实际）

### 2.1 通用

```bash
rustup toolchain install stable
rustup target add x86_64-unknown-linux-gnu aarch64-unknown-linux-gnu x86_64-pc-windows-gnu
sudo apt-get install build-essential pkg-config
rustc --version   # 1.0.2 使用 1.99.1
```

`ring` 需要 C 编译器；不需要 OpenSSL 开发包。

### 2.2 Linux x86_64 v1–v4

```bash
# v1：LLVM baseline 名称是 x86-64，不是 x86-64-v1
CHRONOSYNC_BUILD_TIME=20261105-200000 CHRONOSYNC_BUILD_VARIANT=x86-64-v1 \
RUSTFLAGS='-C target-cpu=x86-64' CARGO_TARGET_DIR=target/dist-v1 \
cargo build --release --locked

# v2/v3/v4
for v in 2 3 4; do
  CHRONOSYNC_BUILD_TIME=20261105-200000 CHRONOSYNC_BUILD_VARIANT="x86-64-v$v" \
  RUSTFLAGS="-C target-cpu=x86-64-v$v" CARGO_TARGET_DIR="target/dist-v$v" \
  cargo build --release --locked
done
```

`x86-64-v1` 不是当前 LLVM 可识别的 `target-cpu` 名称；v1 使用 `x86-64`。包标签仍为 `v1`，`BUILD-INFO` 写 `x86-64-v1` 表示兼容级别。

### 2.3 Windows x86_64

```bash
sudo apt-get install mingw-w64
export CC_x86_64_pc_windows_gnu=x86_64-w64-mingw32-gcc
export CXX_x86_64_pc_windows_gnu=x86_64-w64-mingw32-g++
export AR_x86_64_pc_windows_gnu=x86_64-w64-mingw32-ar
export CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER=x86_64-w64-mingw32-gcc
CHRONOSYNC_BUILD_TIME=20261105-200000 CHRONOSYNC_BUILD_VARIANT=generic \
cargo build --release --locked --target x86_64-pc-windows-gnu
```

如果报 `dlltool` 缺失，安装完整的 `mingw-w64` 工具链，不要只装 gcc 包。

### 2.4 Linux ARM64

需要 aarch64 GNU 交叉编译器、sysroot 和 binutils：

```bash
sudo apt-get install gcc-aarch64-linux-gnu libc6-dev-arm64-cross
export CC_aarch64_unknown_linux_gnu=aarch64-linux-gnu-gcc
export AR_aarch64_unknown_linux_gnu=aarch64-linux-gnu-ar
export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=aarch64-linux-gnu-gcc
export CFLAGS_aarch64_unknown_linux_gnu="--sysroot=/usr/aarch64-linux-gnu"
CHRONOSYNC_BUILD_TIME=20261105-200000 CHRONOSYNC_BUILD_VARIANT=armv8-a \
RUSTFLAGS='-C link-arg=--sysroot=/usr/aarch64-linux-gnu' \
cargo build --release --locked --target aarch64-unknown-linux-gnu
```

实际构建机使用独立提取的 sysroot 和 binutils；如果 `as` 报缺少 `libopcodes-*.so`，把交叉工具链的 `usr/lib/x86_64-linux-gnu` 加入运行期 `LD_LIBRARY_PATH`（只影响构建工具，不进入产物）。

## 3. 静态 musl 方案

### 3.1 为什么考虑 musl

- 不依赖目标 glibc 版本，适合老系统/精简固件。
- 单文件更容易分发。
- 代价：体积增大；DNS/NSS、locale、时区行为与 glibc 不同；ring 的 C/汇编需要 musl 工具链；需要重新做全部闸门。

### 3.2 x86_64 静态构建

```bash
sudo apt-get install musl-tools
rustup target add x86_64-unknown-linux-musl
export CC_x86_64_unknown_linux_musl=musl-gcc
export CARGO_TARGET_X86_64_UNKNOWN_LINUX_MUSL_LINKER=musl-gcc
cargo build --release --locked --target x86_64-unknown-linux-musl
```

验证：

```bash
file target/x86_64-unknown-linux-musl/release/chronosync
# 期望包含 "statically linked"
ldd target/x86_64-unknown-linux-musl/release/chronosync
# 期望 "not a dynamic executable"
./target/x86_64-unknown-linux-musl/release/chronosync --version
```

如 `ring` 仍调用系统 `cc`，明确设置 `CC_x86_64_unknown_linux_musl=musl-gcc`；必要时清掉该 target 的构建缓存再试。musl 目标通常已是静态 CRT，不需要额外 `+crt-static`；如果使用自定义目标，再加 `-C target-feature=+crt-static` 并验证。

### 3.3 ARM64 静态构建

需要 aarch64 musl 交叉工具链（例如 `aarch64-linux-musl-cross`）：

```bash
rustup target add aarch64-unknown-linux-musl
export CC_aarch64_unknown_linux_musl=aarch64-linux-musl-gcc
export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_LINKER=aarch64-linux-musl-gcc
cargo build --release --locked --target aarch64-unknown-linux-musl
file target/aarch64-unknown-linux-musl/release/chronosync
```

当前 1.0.2 构建环境没有 musl 工具链，因此**没有产出 ARM64 musl 包**。不要把 GNU 产物改名为 static。

### 3.4 静态包的额外验收

静态构建必须重新通过：

- G1–G6；
- 在至少一个 glibc 老系统/精简系统启动；
- NTP DNS 解析（musl resolver）和 UDP 123；
- SSH 密码 + keyboard-interactive；
- 扫描/反向 DNS（musl NSS 行为可能不同）；
- `ldd` 非动态、`file` 静态；
- 包名增加 `static` 标识，`BUILD-INFO` 明确 `libc=musl`；
- 不能混用 1.0.2 动态包哈希或 Release 资产。

## 4. 构建元数据与可复现性

`build.rs` 注入：

```text
CHRONOSYNC_BUILD_TARGET   编译 target
CHRONOSYNC_BUILD_VARIANT  CPU/包变体
CHRONOSYNC_BUILD_TIME     发布构建时间
```

构建命令必须显式设置后两者；`/api/health` 和启动摘要会显示。发布包 `BUILD-INFO.txt` 必须与二进制内值一致。

可复现建议：

- 使用 `--locked`。
- 固定 Rust 工具链版本（`rust-toolchain.toml` 可选）。
- 固定 CPU 变体和 target。
- 记录交叉工具链版本。
- 源码包和二进制包分开；不要把 `target/`、`dist/`、真实凭据打入源码。
- 归档使用固定 mtime/owner；记录 SHA256。

## 5. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `x86-64-v1` 未被识别 | LLVM 只识别 `x86-64` | v1 用 `target-cpu=x86-64` |
| `dlltool` 缺失 | MinGW 包不完整 | 安装完整 mingw-w64 |
| ARM `as` 缺 `libopcodes` | 交叉 binutils 运行库路径 | 设置 `LD_LIBRARY_PATH` 到工具链 |
| `ring` C 编译失败 | 没有 musl-gcc/sysroot | 安装 musl-tools 并设置 CC/linker |
| 老系统 `GLIBC_2.39 not found` | 动态包依赖新 glibc | 用源码/静态包在目标构建 |
| 静态包 DNS 失败 | musl resolver/NSS 差异 | 用 IP/正确 resolv.conf；做 DNS 验收 |

## 6. 当前结论

- 1.0.2 正式发布：动态 glibc、MinGW、ARM64 GNU，已构建并验证。
- 静态 musl：方案可行但**未实施/未验收**；需要独立工具链、完整闸门和新版本发布。
- 本文不构成“静态包已提供”的声明。
